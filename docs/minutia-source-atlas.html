Section 1

1The 10,000-foot view

Minutia turns an OBS screen recording into a meeting report. The whole system is one linear data pipeline with four stages, and every piece of the package exists to run, configure, or wrap some slice of it:

Three ways to run it

The same four stages are reachable through three surfaces, and knowing which one you're in explains almost every "why is this file here?" question:

Hold this thought

The step commands + go path is the one that reached notebook parity in Phase 4 — it is current-best. The orchestrator still summarizes the pre-Phase-4 way (no prompt kinds, no markdown report), and baseline_pipeline is a shim awaiting deletion. Phase 6 exists precisely to collapse the second and third rows into the first.

Section 2

2The module map

The package is a strict layer cake: every arrow points downward. A module may import anything below its layer and nothing above it. When you're deciding where new code goes, find the lowest layer where all its imports are satisfied — that's its home.

The two forbidden-cycle stories

Two design decisions this week exist purely to keep the arrows pointing down. They're worth internalizing because they tell you where shared data must live:

Story one: why model_registry.py exists

The model table (anthropic_models) used to live inside steps/summarize_transcript.py. But three other places need it: the orchestrator validates summary_model against it, config.py needs a default model name, and cli.py builds its --model choices from it. The import chain summarize_transcript → config → orchestrator already exists, so orchestrator → summarize_transcript would have closed a cycle:

steps/summarize_transcript ──▶ config ──▶ pipeline/orchestrator ──▶ ✗ steps/summarize_transcript

The fix is the classic one: push the shared data down. model_registry.py imports nothing, so anyone may import it. summarize_transcript re-exports anthropic_models for backwards compatibility (the notebook and tests reference it there).

Bonus discovery: unifying on the registry exposed that the old config default (claude-4-5-sonnet) was never a valid key — the default summarize path had been raising KeyError, and a long-red test (test_baseline_pipeline_smoke) was this bug in disguise.

Story two: the lazy import inside paths.py

resolve_input_video() raises ConfigurationError, which is defined in config.py — but config.py imports paths.py at module load (for CleanupPolicy). A top-of-file import would cycle, so the import happens inside the function body, at call time:

def resolve_input_video(explicit_path, recordings_dir):
    # Imported here: config.py imports this module at import time,
    # so a module-level import would be circular.
    from .config import ConfigurationError
    ...

Function-level imports are the pragmatic escape hatch when only an exception type crosses a layer boundary. If more than that ever needs to cross, the type should move down a layer instead (the model_registry treatment).

3Foundations: bedrock and plumbing

model_registry.py — the shared vocabulary

src/minutia/model_registry.py · new this week · imports: nothing

A single dict mapping friendly keys to API model IDs and per-1k-token prices, plus the project default. Everything model-related derives from it:

anthropic_models = {
    "claude-sonnet-4-6":  {"name": "claude-sonnet-4-6",           # API id
                            "price_per_1k_input_tokens": 0.003,
                            "price_per_1k_output_tokens": 0.015},
    "claude-haiku-4-5":   {"name": "claude-haiku-4-5-20251001", ...},
    ...  # opus-4-7, opus-4-6, sonnet-4-5, 3-7-sonnet, 3-haiku
}
DEFAULT_SUMMARY_MODEL = "claude-sonnet-4-6"
consumed by
orchestrator.SUMMARY_MODEL_CHOICES = tuple(anthropic_models) → config validation; cli.SummaryModel enum → --model choices; the summarize step's price math.
note the split
Key ≠ API name (claude-haiku-4-5 → dated ID). Users always speak the friendly key; only the API call itself uses ["name"].

logging.py — one logger, contextual columns

src/minutia/logging.py · wraps loguru

Every module does from ..logging import logger and never touches loguru directly. Two ideas matter:

1. Sinks are (re)configured, not accumulated. configure_logging(level, logs_file=None) calls logger.remove() then adds a colored stderr sink; the orchestrator calls it again per run with logs_file=run_root/minutia.log to add a DEBUG file sink inside the run directory.

2. Context rides on every record. The format string prints three extra columns — step | input_file | run_root — defaulting to -. The orchestrator wraps work in:

with logging_context(input_file=..., run_root=...):
    with logging_context(step="extract_audio"):
        logger.info("Running step")   # columns fill themselves

So a single grep on a run log gives you a per-step timeline with no extra plumbing in the steps.

paths.py — where files live, decided once

src/minutia/paths.py · frozen dataclass + two helpers

RunPaths — the orchestrator's filesystem contract

An immutable snapshot of every path a run will touch. Built once by a factory, then passed around; no step ever invents a path string. The factory names the run directory {ISO-date}_{slugified-input-stem} and dodges collisions with _2, _3… suffixes (resolve_run_directory).

RunPaths.from_video_input(input_path, base_output_dir) → RunPaths RunPaths.from_audio_inputs(mic, desktop, base_output_dir) → RunPaths # names run from parent dir .ensure_directories() .cleanup(policy)
runs/2026-07-02_client-sync/          ← run_root
├── audio/
│   ├── microphone_audio.wav          ← .microphone_audio
│   └── desktop_audio.wav             ← .desktop_audio
├── transcripts/                      ← .transcripts_dir

CleanupPolicy — three post-run behaviors

KEEP_ALL (default) · KEEP_FINAL (drop intermediate audio, keep transcript/summary) · CLEANUP_ON_ERROR (delete the whole run dir on failure). Applied by the orchestrator after execute(); cleanup() refuses to delete a directory that doesn't look like a minutia run.

resolve_input_video — the discovery rule

resolve_input_video(explicit_path, recordings_dir) → Path

Explicit path always wins. Otherwise: newest *.mkv by mtime in recordings_dir, with actionable ConfigurationErrors for unset / missing / empty. This one function is why bare minutia process-all and minutia extract-audio now work.

run_metadata.py — the run's receipt

src/minutia/run_metadata.py · pure functions

build_run_metadata(...) assembles a JSON-able dict — status, start/end timestamps, input info (duration + segment count when the merge metadata is available), output paths, and the error string on failure — and write_run_metadata persists it as metadata.json. The orchestrator writes it on both success and failure paths, so every run directory self-describes. Phase 5 extends this idea into a per-report sidecar (prompt kind, model, params, token counts) — the eval substrate.

Nearly 800 lines, but the structure is 30: six builder functions, one dict, three accessors. Everything else is prompt text. The contract every builder satisfies:

The accessors, and the behavior change that matters:

list_prompt_kinds() → list[str] # sorted; feeds CLI choices & future evals get_prompt_builder(kind: str | None) → PromptBuilder # None → DEFAULT_PROMPT_KIND ("minutia") generate_meeting_summary_prompt(notes, info, kind=None) → str # convenience dispatch
Design decision

Unknown kinds now raise ValueError naming the valid kinds. The notebook-era dispatcher silently fell back (and actually had a latent crash: builders.get(kind, 'default') returns the string 'default'). Since the CLI derives its --prompt-kind choices from list_prompt_kinds(), typer rejects bad values before this code even runs — the ValueError protects programmatic callers.

One more resident: get_filename_prompt(content, current_date=None) — the prompt that asks Claude to invent a filesystem-safe, date-prefixed filename for a report. It lives here (not in the step) so all prompt text has one home. New flavors go in this file, get registered in PROMPT_BUILDERS, and every surface — CLI choices, go menu, future eval matrix — picks them up automatically.

Section 6

6steps/ — the four pipeline stages

Each step module is deliberately boring on the outside: one public entry function, strings-in, file-paths-out, loguru inside. The disk contract — exact filenames — is the real interface, because the CLI's skip-if-exists logic reconstructs these names to decide whether work is done.

video_extraction.py — MKV in, two labeled WAVs out

deps: ffmpeg-python · no ML

process_mkv_file(input_mkv, output_dir, *, mic_track_number=3, desktop_track_number=2) → {"microphone": path, "desktop": path}

Four internal moves: ffmpeg.probe the streams → extract every audio stream to audio_track_N.wav (1-indexed, matching OBS) → pick mic/desktop by track number from the filename suffix → copy2 to stable names.

disk out
audio_track_1..N.wav (all tracks, kept) + microphone_audio.wav, desktop_audio.wav (copies)
failure mode
ValueError if either requested track number isn't among the extracted files
known issue
Re-running into a dir with existing outputs may hit ffmpeg's overwrite prompt — unverified against current code; the CLI's skip-if-exists mostly sidesteps it. (Spec: Known Issues.)

audio_transcription.py — Whisper, GPU-aware

deps: openai-whisper, torch

process_audio_files(mic_audio_path, desktop_audio_path, output_dir, whisper_model_name="base", use_gpu=True) → {"microphone": path, "desktop": path}

Loads the model once per file (CUDA if available and requested, FP16 on GPU), transcribes, and saves a JSON per track. Logs speed ratio and peak GPU memory — useful when you start comparing Whisper models later.

disk out
{track}-whisper-{model}_transcription.json ×2 — the model name is part of the filename, so switching models never collides with old outputs (and the CLI skip-check is per-model for free)
JSON shape
{metadata: {source_file, model, language, duration, processed_at, schema_version}, segments: […], text}

transcript_merger.py — two tracks, one timeline

deps: stdlib only · golden-verified ✓

process_transcripts(mic_file, desktop_file, output_file, parse_overlaps=True) → merged dict (also written to output_file)

Pipeline inside: parse_transcript (accepts the JSON schema and the legacy plaintext [0.0 - 2.5] text format; normalizes segment keys) → label every segment with source: microphone|desktop → concatenate and sort by start_time → optionally splice overlap markers → attach metadata (counts, duration, per-source metadata, source files).

Practice vs. capability

parse_overlaps=True is the signature default, but the real workflow always passes False — the golden fixtures were generated that way, and the prompt kinds handle echo/overlap in-prompt instead. The overlap splicer exists and is tested, but treat parse_overlaps=False as the de-facto contract.

verified
Reproduces all four golden 03_merged/ fixtures segment-for-segment (test_merger_reproduces_golden_fixture)

summarize_transcript.py — the money step

deps: anthropic, tiktoken · everything Claude-related lives here

This module accumulated the most change: it now hosts transcript prep, cost estimation, the long-summary loop, and the report writer. Group its nine functions into four clusters:

1 · Prep — transcript JSON → prompt text

load_transcript(path) → dict extract_transcript_text(data) → "[Microphone 12.34] text" # timestamped, sorted — the Phase-4 path prepare_transcript_for_summary(data) → "[Microphone] text" # older, no timestamps — orchestrator still uses

2 · Economics — estimate before you spend

estimate_tokens_and_price(text, model="claude-sonnet-4-6") → (total_tokens, price_usd)

tiktoken count of the prompt + assumed max output (8192), priced from the registry. This feeds the CLI's confirm gate.

3 · Generation — the [CONTINUE] loop

generate_long_summary(text, model_name=…, system_prompt=None, api_key=None, **kw) → str

The workhorse. With a system_prompt (the prompt-kind path) the transcript rides as the user message; without one it falls back to the generic built-in prompt. Every prompt kind instructs the model to end with [CONTINUE] if truncated — the loop detects that sentinel, strips it, appends the partial as an assistant turn plus a "please continue" user turn, and calls again until the summary completes. generate_summary is the single-shot sibling (no loop; the orchestrator's current path).

4 · Reporting — AI-named markdown

get_filename_from_content(content, model_name=…, api_key=None) → str create_markdown_report(content, output_path, model_name=…, api_key=None) → Path

A second, tiny Claude call (max 100 tokens) reads the finished summary and proposes a YYYYMMDD_topic_slug filename; the report is written as <that>.md. So every summarize run = two API calls: one big, one cent-sized.

Interface habit worth copying

Every Claude-touching function takes api_key=None and falls back to resolve_anthropic_api_key(), and validates model_name against the registry before constructing a client. Uniform seams → trivial mocking (one patch point: summarize_transcript.Anthropic) and a clean slot for the Phase-5 SummaryClient protocol.

Section 7

7pipeline/orchestrator.py — the sequential engine

The orchestrator is a small, generic step-runner plus four step definitions. Its vocabulary is a family of dataclasses; learn these five and the module reads itself:

TypeMutabilityRole
PipelineConfigfrozenEverything a run needs: input path, RunPaths, models, tracks, key, cleanup policy. Validates summary_model against the registry in __post_init__.
PipelineStepDefinitionmutablename + runner(config, artifacts) → dict + optional is_enabled(config) predicate (how skip_summary works).
StepProgressfrozenEvent emitted to the callback: step name, StepStatus (PENDING/RUNNING/COMPLETED/FAILED), message, error.
PipelineExecutionStatemutableLive view (orchestrator.state): current step, artifacts so far — inspectable mid-run.
PipelineResultmutableThe outcome: success flag, completed steps, failed step + error, artifacts, duration. .is_partial = some steps done but overall failure.

The execute() loop, in prose

For each enabled step: emit RUNNING → call the runner with the config and a read-only view of the artifacts dict (MappingProxyType) → merge the runner's returned dict into the artifacts → emit COMPLETED. The artifacts dict is the only channel between steps: extract publishes microphone_audio, transcribe reads it and publishes microphone_transcript, merge reads those, and so on. On any exception the loop stops, emits FAILED, writes metadata.json with status: failed, applies CLEANUP_ON_ERROR if configured, and returns a partial result — it never raises. Success also writes metadata and applies KEEP_FINAL.

Two idioms worth noting: the four default runners import their step modules lazily inside the closure, so importing the orchestrator doesn't drag in torch/whisper/ffmpeg; and every step body runs inside logging_context(step=…), which is what makes run logs greppable per step.

The Phase 6 gap — read before touching process-all

The orchestrator's summarize runner is still pre-Phase-4: it uses prepare_transcript_for_summary (no timestamps), the single-shot generate_summary with the generic prompt (no prompt kinds, no notes, no personal info), and writes plain summary.txt (no markdown report, no AI filename). Phase 6's job is to add prompt_kind / notes_path / personal_info_path / generate_markdown to PipelineConfig and route this runner through the same code path the CLI's _summarize_step uses. Until then, process-all produces a noticeably weaker summary than go.

Section 8

8cli.py — the typer surface

The CLI owns all UX policy — discovery, idempotency, cost gates, interactivity — and delegates every unit of real work to steps/. Three structural ideas explain the whole file:

1 · The click-compat bridge

app = typer.Typer(name="minutia", add_completion=False)
# ... @app.callback + 7 @app.command functions ...
main = typer.main.get_command(app)   # ← a genuine click.Command

That last line is why the migration was invisible to everything else: the console-script entry point (minutia = "minutia.cli:main"), the package re-export, and click.testing.CliRunner all still receive a Click object. Typer is an implementation detail behind it.

2 · Enums derived from registries

SummaryModel = Enum("SummaryModel", {c: c for c in anthropic_models}, type=str)
PromptKind   = Enum("PromptKind",   {k: k for k in list_prompt_kinds()}, type=str)

Typer renders enum members as CLI choices, so --model and --prompt-kind can never drift from the registries that validate them. Add a model or a prompt flavor at the source, and the CLI updates itself.

3 · Shared step helpers

The commands are thin wrappers over three private helpers that hold the actual policy — and go chains the same three, which is why guided and piecemeal runs behave identically:

_extract_audio_step(config, video, out_dir, mic, desk, force) # skip if both wavs exist _transcribe_step(config, mic, desk, out_dir, model, gpu, force) # skip if both {track}-whisper-{model}…json exist _summarize_step(config, merged, out_dir, kind, notes, info, model, dry_run, yes) # read context files → estimate → confirm → long summary → AI-named report

The minutia go sequence

Error-handling convention

Every command body follows the same shape: helpers raise click.ClickException for user-facing errors (typer sits on click, so these render as Error: … with exit 1); generic exceptions are logged with traceback then re-wrapped; click.exceptions.Abort (a declined confirm) passes through untouched. If you add a command, copy that try/except ladder.

Section 9

9Data contracts on disk

Files are the real interfaces between stages — each one is versioned (schema_version: "1.0") and self-describing. The three JSON shapes:

Per-track transcript — written by transcribe, read by merge

{
  "metadata": {
    "source_file": "…/microphone_audio.wav",
    "model": "medium.en",           ← which Whisper produced this
    "language": "en", "duration": 1834.2,
    "processed_at": "2026-07-02T18:04:11+00:00",
    "schema_version": "1.0"
  },
  "segments": [ { "start_time": 0.0, "end_time": 2.76, "text": "…",
                  "id", "tokens", "temperature", "avg_logprob",
                  "compression_ratio", "no_speech_prob" } , … ],
  "text": "full transcript as one string"
}

The merger's _normalise_segment also accepts start/end key variants and a legacy plaintext format — the compatibility shim that let old notebook outputs keep working during migration.

Merged transcript — written by merge, read by summarize

{
  "metadata": {
    "schema_version": "1.0", "parse_overlaps": false,
    "segment_count": 23, "total_duration": 1834.2,
    "sources": { "microphone": {…track metadata…}, "desktop": {…} },
    "source_files": { "microphone": "…json", "desktop": "…json" }
  },
  "transcript": [ { …segment fields…, "source": "microphone" | "desktop" }, … ]
}

Note the key rename: per-track files say segments, the merged file says transcript — and each entry gains the source label the prompt kinds rely on ([Desktop]/[Microphone] speaker mapping).

metadata.json — the orchestrator's receipt

{ "schema_version": "1.0",
  "run_info": { "started_at", "completed_at", "status": "completed"|"failed", "error"? },
  "input":    { "source_file", "duration"?, "segment_count"? },
  "outputs":  { …paths that exist…, "logs" } }

Written on success and failure — a run directory always explains itself. Phase 5 adds the per-report sidecar next to each .md (prompt kind + hash, model, params, token counts, cost) so every real run becomes an eval datapoint.

Section 10

10Cross-cutting threads

Four journeys that cross many modules — tracing them is the fastest way to feel fluent.

Where a model name travels

model_registry.anthropic_models (friendly key) → config.summary_model default / env / file → possibly overridden by --model (enum whose members are the registry keys) → _summarize_step(model_name) → validated again inside generate_long_summary → translated to the API ID via ["name"] only at the client.messages.create call. One vocabulary, one translation point.

Where the API key travels

Layered lookup in load_config (three names × all layers) → config.anthropic_api_key → passed explicitly as api_key= by the CLI and orchestrator → each step function falls back to resolve_anthropic_api_key() (os.environ) only if not given. The dotenv mutation in _load_env_files keeps that fallback working for notebook users who never touch config objects.

Where "which file do I process?" is decided

Explicit CLI argument → else resolve_input_video picks newest .mkv in recordings_dir → in go, the same ordering feeds a pick list instead (and an optional directory argument overrides the configured dir). All three routes echo the chosen file — discovery is never silent.

The two output layouts (the subtlety most worth remembering)

Step commands + goprocess-all / baseline
LayoutFlat directory (go: <base>/<recording-stem>/)RunPaths tree: <base>/<date>_<slug>/audio/…
Naming authorityThe step functions' own conventionsRunPaths dataclass
Collision policySkip-if-exists (idempotent re-entry)New suffixed dir per run (_2, _3…)
Re-run costOnly missing stages runEverything runs again
Why both exist

The flat layout mirrors the notebook's one-folder-per-meeting habit and makes skip-if-exists trivial (stable names). RunPaths gives the orchestrator collision-proof, self-contained run directories. Phase 6 will have to pick a reconciliation — most likely teaching the orchestrator the skip-aware helpers rather than the other way around.
